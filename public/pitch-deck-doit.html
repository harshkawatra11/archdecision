Problem Statement

The reasoning behind a codebase evaporates.

The engineer who chose the datastore leaves. The chat thread that explained it is gone. New engineers spend weeks rediscovering context, and teams repeat mistakes they already solved.
Why it persists

Architecture Decision Records are the known best practice for capturing this. Almost nobody writes them, because doing it by hand is tedious work with a delayed payoff. The context keeps disappearing, one departure at a time.

The opening

One source of truth never leaves: the code. Dependencies, file structure, configs, and entry points still hold the evidence for why the system looks the way it does. That evidence is just never read as a decision record.

Solution

Recover the decisions from the code, write the record itself.

What it does
  • 01
    ADR generator. 5 to 8 records in the Nygard format, each with the evidence it was inferred from.
  • 02
    Ask your codebase. Plain-English answers scoped to the repo, with file citations.
  • 03
    Onboarding doc. A day-one guide to how the codebase works, ready to commit.
  • 04
    PR architectural review. Checks a pull request against the generated ADRs.
  • 05
    Tech-debt drift map. Where the code diverged from the decisions it was built on.
How we built it
Frontend. React, Vite, TypeScript, Tailwind.
Backend. Vercel serverless functions in Node and TypeScript, streamed over SSE.
Model. Gemini 2.5 Flash behind a swappable OpenAI-compatible interface. No database, no auth, no paid services.
Decision points
  • Grounding over generation. Never the raw repo, only a compact RepoProfile within a token budget.
  • Repo content is data, not instructions. Analyzed, never followed.
  • Swappable model layer. Groq, OpenRouter, or GitHub Models by env vars. Key stays server-side.
