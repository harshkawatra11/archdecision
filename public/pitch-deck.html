Problem Statement

The reasoning behind a codebase evaporates.

Codebases are full of decisions whose reasoning is gone. The engineer who chose the datastore left. The chat thread that explained it is gone. New engineers spend weeks rediscovering context, and teams repeat mistakes they already solved.

Architecture Decision Records are the known best practice for capturing this. Almost nobody writes them, because doing it by hand is tedious work with a delayed payoff. So the context keeps disappearing, one departure at a time.

There is one source of truth that never leaves the building: the code. The dependencies, the file structure, the configs, and the entry points still hold the evidence for why the system looks the way it does. That evidence is just never read as a decision record.

03 / 06
Solution

Recover the decisions from the code, write the record itself.

What it does

ADR generator. Architecture Decision Records in the Nygard format, each with the evidence it was inferred from.
Ask your codebase. Plain-English answers scoped to the repo, with file citations.
Onboarding doc. A day-one guide to how the codebase works, ready to commit.
PR architectural review. Checks a pull request against the generated ADRs.
Tech-debt drift map. Where the code has diverged from the decisions it was built on.

How we built it

Frontend: React, Vite, TypeScript, Tailwind.
Backend: Vercel serverless functions in Node and TypeScript, streamed over SSE.
Model: Gemini 2.5 Flash behind a swappable OpenAI-compatible interface. No database, no auth, no paid services.

Decision points

  • Grounding over generation. Never send the raw repo, only a compact RepoProfile within a token budget.
  • Repo content is data, not instructions. It is analyzed, never followed.
  • Swappable model layer. Point it at Groq, OpenRouter, or GitHub Models by changing env vars. The key stays server-side.
